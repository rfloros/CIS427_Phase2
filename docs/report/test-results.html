What the key tests showed. Simultaneous answers each counted once with correct scores (T36); a same-name join race gave one 200 and one 409 (T37); ending game A left game B running (T38); three stalled readers in one game did not delay another game's replies beyond 500 ms (T40), while the earlier single-lock design failed that test in 5 of 6 runs; a lobby with an absent host ended with HOST_EXPIRED and a started game ran on to COMPLETE (T42, T47); a join in the final intermission appeared in the final results (T43); and failed thread launches, shutdown, and thread cleanup behaved as designed (T44). Testing also found one real bug, a reply that could be written after GAME_END; it was fixed and covered by a regression test.

Restart behavior (T51). With a game running, the server was stopped (once with SIGINT and once with SIGKILL) and started again on the same port. Both players’ connections were closed. The old host and player tokens then got 410, the old join code got 404, and a new game could be created at once. Games live only in memory, so a restart ends every game; this is the documented behavior (section 11).

Load test (T52). Every client joins a game, then sends its requests one at a time and waits for each reply. Nine in ten requests are LEADERBOARD and one in ten is an invalid line, which must get a 300 reply without disturbing anyone else. A request counts as failed if its reply is wrong or takes more than 5 seconds. The games stay in the lobby, so no timed pushes arrive between a request and its reply.

What it showed. No request failed, the server never crashed, and it stopped cleanly with SIGINT afterwards. Threads equal the clients plus the games plus one, as designed. Response times rose from about 35 ms to about 155 ms and throughput stopped growing at roughly 1 000 requests per second. The test clients are bash processes sharing the same 2 CPUs as the server, so these times include client overhead and are best read as a comparison between runs. The slowest reply in the 210-client run took 1.2 s, above the 500 ms limit in NFR-01; that limit covers up to 20 players on a lightly loaded machine, so it is a sign of where thread-per-client starts to slow down, not a failed requirement.

Limits of this evidence: one machine, localhost only, timed play with at most 20 players in one game, a load test that stays in the lobby and uses a bash client on 2 CPUs, and timing bounds that assume a lightly loaded machine.
