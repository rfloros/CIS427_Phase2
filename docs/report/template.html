2. Final problem statement and value proposition

Problem. Casual groups (dorm friends, campus clubs) lack a lightweight way to play fair, scored trivia together without accounts, payment, or a browser. Reading questions aloud has no reliable scoring or leaderboard and invites arguments about who answered first.

Solution. TermTrivia is a client-server terminal game over TCP. One server hosts many games at once. A host creates a game with a join code, players join with the code, and after START_ROUND the server runs the whole game on timers: a 20-second question, a 5-second intermission, and a 10-second final intermission. Scores come from correct answers only. A player who disconnects can reconnect within 60 seconds with a private token and keep their score.

Value proposition. For casual campus groups who need a fast, fair way to play trivia together, TermTrivia provides a lightweight, terminal-based multiplayer quiz game joinable with a simple code. Unlike Kahoot or Quizizz, it needs no account, no web client, and no payment. Its distinctive feature is correctness-only scoring, which two interviewed classmates preferred to speed-based scoring and which keeps the game fair for slow typists.

4. Architecture diagram

Source: docs/images/architecture_diagram.svg (PNG and PDF copies alongside).

Each client has a main thread (prompt), a reader thread (the only caller of recv), and a reply queue. The server has an accept loop, one handler thread per client, one timer thread per game, a lock ("lane") per game, a short routing lock, the game-state object, the logger, and the question bank.

6. Concurrency design

Threads. The accept loop starts one handler thread per connection; the handler owns that connection and is the only reader of its socket. Each game has one timer thread that ticks only that game every 20 ms. Writes can come from a handler (replies, and pushes caused by that command) or from the timer thread (question, result, and end pushes).

Per-game lane. The server first used one global lock for all games, which kept messages in order but let one slow client delay everyone. With three clients in one game not reading, a reply in another game took longer than 500 ms, and the test T40 failed on that design (5 of 6 runs). The final design gives every game a lane, a mutex that is held from the state change until all of that event's messages are written. That keeps reply-before-push and the order of events inside a game, while different games write at the same time.

Lock order is always: the game's lane (or the connection's own lane when it is not in a game), then the short routing mutex, then the game manager's own mutex. The routing mutex protects the game-code-to-lane map and the connection map. It may cover a state change and a registry update, but never a socket call. Because every path uses the same order, threads cannot deadlock.

Choosing the lane. A command takes the lane of the game the connection is in; JOIN_GAME and RECONNECT use the code in the command. After locking, the server looks the lane up again, and retries if the game was removed or replaced, so a stale lookup never touches a newer game that reuses the code.

Creating a game. CREATE_GAME holds the new game's lane before the game is published, starts the game's timer thread, and only then writes 200 OK. If the timer thread cannot start, the game and lane are rolled back while the lane is still held, so a concurrent JOIN_GAME cannot enter a game that is about to disappear, and the connection is closed with no reply. This resource-exhaustion path is the one exception to the one-reply rule (T44).

Delivery and lifetime. Each effect is paired with a shared_ptr to its connection while the state change is protected, then written outside the routing mutex under the connection's own write lock with a 200 ms send timeout. A connection stays alive until the last pending write finishes, so no write can reach a closed or reused descriptor.

Cleanup and shutdown. Every worker sets a done flag as its last step. The accept loop joins finished workers after each wake-up; at shutdown it stops accepting, lets handlers and timers see the stop flag (handlers poll every 50 ms), and joins handlers first and timers second. If a handler thread cannot be created, that connection is closed and the error is logged while the server keeps accepting (T44).

Host expiry. The timer thread expires reconnect windows. An expired host in a lobby ends the game with GAME_END HOST_EXPIRED; during play the host is just removed (T42, T47).

7. Protocol specification

Full text: docs/protocol.md. The protocol is line-oriented ASCII over TCP. A client message is one line ending in a newline. A server message is one or more lines followed by a blank line; a reply is the answer to exactly one command and a push starts with PUSH.

CommandMeaning and success reply
CREATE_GAME <name> <count>200 OK, join code, private token
JOIN_GAME <code> <name>200 OK, “N players in game CODE”, token
START_ROUND (host)200 OK, then PUSH QUESTION 1 to every active player
SUBMIT_ANSWER <A-D>200 OK (correctness is revealed in ROUND_RESULT)
LEADERBOARD200 OK, then name:score lines, highest first
RECONNECT <name> <code> <token>200 OK, “score question-number”, and the open question again
QUIT200 OK, then the connection closes
END_GAME (host)200 OK, then GAME_END HOST_ENDED to everyone

Pushes: PUSH QUESTION n text with options A to D; PUSH ROUND_RESULT n with the correct answer and standings; PUSH GAME_END reason with final results. End reasons: COMPLETE, HOST_ENDED, HOST_QUIT, and HOST_EXPIRED (new in Phase 3). Error codes: 300 format, 401 not in a game, 402 host only, 404 unknown code, 409 duplicate name, 410 reconnect refused (one generic reply for any wrong detail), 420 no open round, 421 already started, 422 already answered, 423 bad question count. Phase 3 additions are recorded in docs/design-changes.md (decisions 38 to 43).

9. Error-handling strategy

  • Bad input: every empty, unknown, malformed, or over-long line gets one error reply and the connection stays open. Input is data only and is never executed.
  • Wrong state: specific codes (401, 402, 404, 409, 420 to 423) say what was wrong; no state changes.
  • Reconnect secrecy: every wrong name, code, token, or late reconnect gets the same 410.
  • Slow or dead clients: writes time out after 200 ms and mark the connection broken; the handler treats it as an unexpected disconnect. Resets and closes are handled the same way; SIGPIPE is ignored and sends use MSG_NOSIGNAL.
  • Disconnects: the player is kept for the reconnect window and does not hold up a round; the server keeps running.
  • Host never returns: a lobby ends with HOST_EXPIRED; a started game continues without a host.
  • Resource failure: a handler thread that cannot start closes that client; a timer thread that cannot start rolls back the new game with no reply. Both are logged and the server keeps accepting.
  • Shutdown: Ctrl+C stops accepting, ends every worker within about 50 ms, joins them, and logs one line.
  • Logging: connections, requests with result codes, errors, game events, disconnects, and shutdown are logged; tokens never are.

10. Test results

11. Known limitations

  • One thread per client and per game: simple, and sound for the tested scale, but not for thousands of clients.
  • A client that stops reading costs its own game up to 200 ms of waiting per write before it is dropped.
  • No host transfer; no persistence; all games are lost if the server stops.
  • No encryption and no user accounts; reconnect safety rests on a four-character private token. All testing used localhost and one machine, never a real network, never more than 20 players.
  • A terminal and typing are required; a question still closes after 20 seconds.
  • The client lists a join code but cannot browse games; there is no chat, team mode, or custom timer per question.

14. Ripple Report reflection

Part A: Effects on users

Greatest value. Two features created the most value: correctness-only scoring and reconnect. When two players know the material, they tie, and it does not matter who types faster. That also removes the typing-speed gap, since players type commands in a terminal. Reconnect fixes a problem that games like Kahoot have, where a player who gets disconnected cannot rejoin. A crash or an accidentally closed window no longer ends a player’s game.

Reliability. The decision that improved reliability most was the reconnect token with a 60-second window. A dropped player keeps their name and score, and nobody else can take their place. Closing a round as soon as every active player has answered, and giving each game its own lock, also kept games moving and kept them independent.

Hardest part of the interface. Typing commands correctly: the spelling, and the order of arguments such as name before question count. We made these mistakes ourselves while testing. The client lists the commands at the start and shows a Usage: line when a command is typed wrongly.

Error handling and trust. The server answers a bad request with an error and keeps the connection open, so the player can try again. One typo does not break the game. This made it feel sturdier and more real.

A user assumption. We assumed players would prefer fairness over speed, and the people we interviewed did. Others we talked to enjoy the speed pressure, so correctness-only scoring is a plus for some players and takes away intensity for others.

Evidence the application solves the problem. In our interviews, two classmates said that speed-based scoring is annoying even when you answer correctly, and that being unable to reconnect after a disconnect is a problem. Both are addressed by the final design. The automated tests also pass (see section 10).

Part B: Effects on teammates

Protocol and parallel work. At the start of Phase 1 we met for a couple of days to agree on the big decisions: correctness-only scoring and some form of reconnect. With those settled, the details fell into place and each of us could work on our own documents without contradicting the other. We worked in a shared Google Doc, with each document in its own tab, and we sat together to ask questions.

Helpful documentation. The tabbed shared Google Doc let each of us see what the other had done. We also used AI agents to summarize what had changed, so each of us stayed up to date.

Rework. The rework we had to do came from the professor’s grading comments on Phase 1, which said the protocol, requirements, and test plan needed fixes. It did not come from confusion between the two of us.

Resolving ideas. We rarely disagreed. Our main discussion was how reconnect should work so that nobody could take a disconnected player’s name. We asked the agents for options, discussed them, and chose the one that fit the scope of the project.

What we would change. We would meet and talk more toward the end of the project, as we did at the start.

Part C: Effects of networking decisions

Decision 1: Reconnect token and 60-second window.

  • Decision: Each player gets a private token when they join or create a game. To reconnect, the player must present their name, the game’s join code, and the token within 60 seconds.
  • Why: We wanted dropped players to be able to return, but we had to stop someone else from reconnecting with a disconnected player’s name and taking their place.
  • Benefit: Dropped players keep their score, and nobody can take over their seat.
  • Tradeoff: If the host leaves, the game keeps running on its timers and ends by itself, but nobody can end it early or use the host’s controls.
  • What we would change: Add host transfer, so the host’s permissions pass to another player.

Decision 2: One lock per game.

  • Decision: Each game has its own lock, and the server runs one thread per client.
  • Why: Several games can run on one server, and separate groups of friends should not slow each other down. A single global lock was our first design. The team’s testing showed it let slow clients in one game delay other games, and the test failed in 5 of 6 runs (T40, section 10), so we moved to one lock per game.
  • Benefit: Games run independently of each other.
  • Tradeoff: A client that stops reading still delays its own game, by up to 200 ms per message, and a thread per client does not scale to thousands of connections.
  • What we would change: Give each client an outgoing message queue and move to an event loop or thread pool.

Decision 3: No persistence (games exist only in memory).

  • Decision: Only the question bank is stored in a file. Active games and scores exist only in memory.
  • Why: This is a class project. Saving anything else would have been a lot of extra work and was not needed for what the project was aiming to do.
  • Benefit: The design is simpler, and there is no file handling to get wrong.
  • Tradeoff: If the server stops or crashes, all games and scores are lost.
  • What we would change: Save game state in a database so it survives a crash, and so players could replay the same set of questions.

Part D: Scale reflection

If this were used by hundreds or thousands of people, the first thing we would improve is the concurrency model. We would replace one thread per client with an event loop: one thread watches all the connections and handles whichever has data ready. Thousands of threads cost too much memory and switching time. The tradeoff is that each piece of work must be short, or it would hold up every client. We would pair this with a per-client outgoing queue so a slow reader cannot delay a broadcast. After that, we would add persistence, as described above.
